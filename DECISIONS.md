# Решения проекта Ватага

## Архитектурные решения

### 1. PeerJS public cloud вместо собственного сервера
**Решение**: Используем PeerJS public cloud (0.peerjs.com)
**Причина**: Zero-config, не нужен аккаунт, работает из коробки. Для 2-8 человек в комнате — достаточно.
**Альтернативы**: Supabase Realtime, Firebase, свой WebSocket — оставлены как замена через signaling.js

### 2. Vanilla JavaScript вместо фреймворков
**Решение**: Чистый JS без React/Svelte/Vue
**Причина**: Минимум зависимостей, быстрая сборка, маленький бандл (~113 КБ gzip). Один экран — фреймворк избыточен.

### 3. Mesh-топология вместо SFU
**Решение**: Каждый с каждым (mesh)
**Причина**: Нет медиа-сервера = нулевая стоимость. Для 2-8 человек mesh работает приемлемо. СФУ потребовал бы сервер.

### 4. Vite как сборщик
**Решение**: Vite 5.x
**Причина**: Быстрая HMR-разработка, esbuild для продакшена, нативная поддержка ES-модулей.

### 5. Тёмная тема по умолчанию
**Решение**: GitHub-style dark palette
**Причина**: Голосовые чаты обычно используют в тёмное время. Тёмная тема — стандарт для Discord/TeamSpeak.

### 6. Opus 48 kHz стерео 128 кбит/с
**Решение**: Opus через WebRTC (по умолчанию)
**Причина**: Лучший кодек для голоса. WebRTC автоматически выбирает Opus. 48 kHz — максимум для Opus.

### 7. Чанки 32 КБ для передачи файлов
**Решение**: RTCDataChannel с чанками 32 КБ
**Причина**: Оптимальный баланс между overhead и латентностью. DataChannel имеет лимит ~256 КБ на сообщение, 32 КБ — безопасно.

### 8. Потоковая запись файлов
**Решение**: Сборка чанков в Blob после получения всех
**Причина**: Простота реализации. Для файлов 10+ ГБ нужно стриминговое решение, но для MVP Blob достаточен.

### 9. STUN Google + TURN Cloudflare
**Решение**: stun.l.google.com:19302 + turn.cloudflare.com:3478
**Причина**: Бесплатные, надёжные, покрывают большинство NAT-сценариев.

### 10. Perfect negotiation pattern
**Решение**: Полite/impolite peer на основе сравнения peerId
**Причина**: Стандартный паттерн для решения glare (одновременный offer). Сравнение строк — простая детерминация ролей.

### 11. CSS — нативный, без препроцессоров
**Решение**: Обычный CSS с CSS-переменными
**Причина**: Минимум зависимостей. CSS-переменные достаточны для тёмной темы.

### 12. esbuild вместо terser для минификации
**Решение**: esbuild (встроен в Vite)
**Причина**: terser требует отдельной установки. esbuild быстрее и уже есть в Vite.

## UI/UX решения

### 13. Код комнаты — 6 символов
**Решение**: A-Z, 2-9 (без O/0/I/1 для избежания путаницы)
**Причина**: Достаточно уникальности для малых комнат, легко читается.

### 14. VU-метр на аватаре
**Решение**: Зелёная полоска под аватаром участника
**Причина**: Визуальная индикация говорящего без звуковых артефактов.

### 15. Лог событий в комнате
**Решение**: Моноширинный лог с таймстемпами
**Причина**: Отладка и история действий. Лимит 500 записей.

### 16. Архитектура комнаты: хост-модель
**Решение**: Первый участник создаёт PeerJS peer с ID комнаты, остальные подключаются к нему
**Причина**: PeerJS не имеет встроенной поддержки комнат. Хост слушает на предсказуемом ID (vataga-<код>), newcomers подключаются к нему. Хост рассылает список участников новичкам и уведомления о новых участниках — остальным. После этого участники соединяются напрямую (mesh) для медиа.

### 17. Оптимизация рендера
**Решение**: Кеширование HTML строк, обновление только при изменении
**Причина**: VU-метр обновляется каждые 150мс. Без кеширования — пересоздание DOM каждый тик = утечки и лаги.
